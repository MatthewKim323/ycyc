# T3 Code teardown for ycyc

Source: https://github.com/pingdotgg/t3code (MIT, ~61.5k stars, pushed 2026-11-15). Read via `gh api` on 2026-11-15. Paths below are repo-relative.

## 1. How T3 Code is built

- **Server owns everything.** `apps/server` runs provider processes, terminals, git and files. Clients (`apps/web`, `apps/desktop` Electron that bundles a server, `apps/mobile` Expo) are remotes over authenticated RPC + WebSocket. Shared connection logic lives in `packages/client-runtime`; the wire contract is `packages/contracts/src/rpc.ts`. Event sourced: the orchestrator records intent, an effect worker does I/O after commit, command receipts make retries idempotent (`docs/internals/overview.md`).
- **Provider abstraction.** One interface, `ProviderAdapterV2` (`packages/provider-core/src/server/ProviderAdapter.ts`). A driver is an integration, an instance is one account (two Claude accounts never share state). Each provider is its own package exporting `./settings`, `./client`, `./server`, `./testing` (`docs/internals/adding-a-provider.md`). Rules: capability flags must match what the provider really does; never fake a permission mode by answering approvals in T3; background health checks must never open a session or trigger a login. Long tail goes through the generic ACP adapter + the external ACP Registry (`docs/user/providers-acp.md`).
- **Approval protocol.** Request kinds `command | file-read | file-change | mcp-elicitation | permission`; decisions `accept | acceptForSession | acceptAlways | decline | cancel`; each option can carry a `warning`; provider option IDs pass through unchanged (`packages/contracts/src/providerPolicy.ts`). Modes are ranked Supervised < Auto-accept edits < Auto < Full access, and any grant can carry a mode ceiling. Requests are persisted and survive restarts; if the provider process died the card says it can't respond instead of pretending (`RuntimeRequestService.ts`). Phone card defaults: **Allow once / Allow session / Decline** (`apps/mobile/src/features/threads/PendingApprovalCard.tsx`).
- **Push.** Relay Worker sends APNs/FCM only on phase *transitions* (needs approval, needs input, done, failed), with per-phase toggles. Several at once become "3 agents need attention". Done/failed alerts older than 2 min are dropped, waiting rows expire at 24 h, nothing buzzes on replay. Pushes aren't actionable: tap opens the thread. Lock screen shows title + status only (`infra/relay/src/agentActivity/agentActivityAlerts.ts`, `docs/user/mobile-notifications.md`).
- **Pairing.** `t3 pair` prints a QR + one-time link with the token in the URL **fragment** (`https://host/#token=...`, `apps/mobile/src/features/connection/pairing.ts`), so it never reaches server logs. It's swapped for a scoped session; scopes can narrow, never widen. T3 Connect = Clerk login + a relay that mints a one-time DPoP-bound bootstrap credential and a Cloudflare tunnel. The relay never sees the session token or proxies traffic. Optional "Require approval for new devices" shows a matching code (`K7QM-2XFD`, 10 min expiry) (`docs/internals/t3-connect.md`, `docs/internals/environment-auth.md`, `docs/user/remote-access.md`).
- **T3 is also an MCP server for outside agents** (ChatGPT, Claude, Codex, Poke) at `/mcp`: OAuth with PKCE, public clients, stateless registration. The approval page names who gets the access ("Anyone who runs that service gets the access"). The user picks **Read only** or a mode ceiling. Each agent shows up in Sharing & access, can be revoked on its own, and has to re-approve after 30 days. Every tool must declare read vs write or it won't compile (`apps/server/src/mcp/McpToolAccess.ts`). Deferred tools: clients see 4 direct tools + `tool_search`, and found tools get listed with `tools/list_changed` (`apps/server/src/mcp/McpToolExposure.ts`, `docs/user/outside-agents.md`).

## 2. What transfers, ranked (impact / effort)

| # | Pattern | T3 | ycyc today | When |
|---|---|---|---|---|
| 1 | Credentials never in shareable text | "Treat pairing URLs and codes as passwords"; token in fragment, one-time | `connectUrl()` in `convex/lib/mcp.ts` prints `/connect/<slug>?u=<mcpToken>` into the chat; the `/connect` handler in `convex/http.ts` never reads `u`. Every chat transcript or shared chat leaks the full MCP credential | **Today, 2 min** |
| 2 | Approval options with scope + warning | Allow once / Allow session / Decline, `warning` per option | Approve / Deny only (`src/components/rows.tsx`) | **Today** |
| 3 | Waits that don't cancel | Wait timeouts return `waitTimedOut: true` and leave work pending; retries dedupe on `clientRequestId`; notes native MCP clients cut requests at ~60 s | 20 s poll, then the approval is expired and the AI is told to retry (`APPROVAL_WAIT_MS`), and a retry makes a new approval | **Today** |
| 4 | Per-assistant OAuth sessions, read-only vs writes ceiling, revoke per client, 30-day expiry | `/mcp` OAuth + Sharing & access | One permanent token per user, no rotation, shared by every assistant; `users.get({userId})` returns it | After (rotate button today) |
| 5 | Secrets never readable back | "Only the creation response returns the raw credential" | mcpUrl is readable from any query that has the userId | After |
| 6 | Search + lazy tool listing | `tool_search` + `list_changed` | Every `<slug>__<tool>` listed up front | After (matters past ~10 apps) |
| 7 | Push on transitions, coalesced, no args on lock screen | relay | No push yet (no `expo-notifications`) | After |
| 8 | Honest capabilities; health checks never log in | adapter rules | Strong needs an emailed MFA code on every password login: a `verify` that re-logs in emails the user | After, important for Strong |
| 9 | Replay fixtures from recorded traffic | "A test that drives the adapter with hand-written frames is a guess about the protocol" | Capture exists; no recorded-fixture regression per recipe | After |

**Provider vs recipe abstraction.** T3 adapters are code over a CLI that already exists and the labs sanction. Our "provider" is a JSON recipe run by a fixed executor (device / cloud / phone). Same rules carry over: one instance per user account (executor must never reuse another user's cookies), honest per-tool `kind`, and an explicit `verify` separate from health polling. Our version is cheaper to add (data, not code, and App Store safe) but breaks more often (no vendor contract), which is why #9 matters.

**Positioning, their words.** README: "**Your subscriptions.** T3 Code does not resell tokens. It drives the agents you are already signed in to." FAQ: "There's no way to pay us... You bring your own sub." "Does my code go to T3 servers? No... Our relay sets up the link. It does not proxy your HTTP or WebSocket sessions." They also refuse a multi-account auto-switcher because it risks ToS bans. For ycyc: borrow "bring your own assistant, we run zero inference" and "credentials per user, only API shapes shared." **Don't** borrow "never touches our servers": the cloud executor path does proxy calls through Convex. Say it only for the device path.

**Community model.** `CONTRIBUTING.md` auto-closes outside PRs for new providers or features ("If you're looking for things to contribute... Don't."), caps 3 open PRs per person, and sends the long tail to the external ACP Registry (spec-conformant, SHA-256 checked installs). The bottleneck they name is review capacity. Lesson: a recipe registry beats a recipe PR queue. Accept a community recipe automatically once a recorded capture replays and a live `auth.check` + reads pass on a real account (`draft | verified | broken` already exists in `apps.list`).

**Dev surfaces.** `curl -fsSL https://t3.codes/install.sh | sh`, `npx t3@latest`, `t3 up` (pick Connect/LAN), `t3 pair` (QR), `t3 thread start . "..."` for scripts, and copy-paste `claude mcp add --transport http t3 <url>` + `claude mcp login t3`. ycyc mirror: `npx ycyc add claude|cursor|codex` (runs the `mcp add` line, pairs via QR scanned by the phone, device-code style like their SSH flow) and `npx ycyc capture <url>` (opens a browser, records fetch/XHR while you click, runs `src/lib/compiler` into `recipes/<slug>.json` as a draft, then `npx ycyc verify <slug>`). Capture is the contributor on-ramp for the registry.

## 3. Ship today (under 30 min each)

1. **Take the token out of connect links.** In `convex/lib/mcp.ts`, `connectUrl()` drops `?u=${token}`. The phone already knows the user from its device ID. Optional: stop returning `mcpUrl` from `users.get`.
2. **Third approval button + warning.** "Allow for 1 hour" stores a grant on (user, assistant, app, tool) with `expiresAt`; `callAppTool` skips the approval when a live grant matches. Add an optional `warning` to the approval (ParkMobile `start_parking`: "Charges your card"; Flo: "Health data") and show it on the card. Files: `convex/approvals.ts`, `convex/lib/mcp.ts`, `src/components/rows.tsx`.
3. **Approvals that outlive the 20 s wait.** On timeout, keep the approval pending (expiry ~10 min) and return "Waiting for approval on the phone (id X). Call `check_approval` with this id." Dedupe on a hash of (tool, args) so a retry reuses the pending approval and never logs lunch twice. Backup if time is short: a "Rotate link" button (`users.rotateToken`).

**Pitch only:** (a) per-assistant OAuth with "Read only / Approve writes", the same flow T3 uses to plug into ChatGPT and Claude; (b) a recipe registry where a recipe is only marked verified after its recorded traffic replays, the ACP Registry model for consumer apps; (c) `npx ycyc capture`: any logged-in website becomes a recipe in one command.
