# Agent-led app API learning

Both hosted native agents receive Yuzu's discovery and learning MCP tools automatically. They can research a requested app, inspect the user's captured request schemas, and create immutable private read tools or evidence-backed write tools. Reads are checked against the real endpoint; writes receive only a structural dry run and require a separate one-time approval before execution. Neither native runtime receives a shell, arbitrary code execution, raw source/capture bodies, or session credentials.

## Workflow

1. `search_apps({query})` finds App Store apps. `investigate_app({app})` accepts a returned app slug or a public HTTPS website URL. It reads public HTML/JavaScript/documentation and returns same-origin source IDs and endpoint evidence IDs. Follow a source with `investigate_app({app,sourceId})`.
2. For authenticated data, `connect_app` opens the existing mobile sign-in/capture flow. Unknown web apps finish at **Capture ready**, then return to the in-app agent. Their captures no longer create or publish global recipes. `inspect_app_capture({app})` returns evidence IDs, endpoint paths, methods and request/response schemas, never recorded values or credentials. A learned write requires `write_endpoint` evidence from an observed same-origin action in the user's capture; public-source research cannot authorize writes.
3. `build_app_tool({app,evidenceId,name,title,kind?,responsePath?})` creates a private immutable draft. `kind` defaults to `read`; `write` requires matching captured write evidence. The server derives the request and allowed arguments from that evidence. The model cannot supply a request URL, header, method, raw body template, login exchange or executable code.
4. `verify_app_tool({toolId,args?})` checks reads against the real endpoint and requires a successful JSON object/array at the selected response path. For writes it performs a **local structural dry run only**: no network request, replay or app mutation. Its receipt says `validation: "structural_only"` and `executed: false`. A write dry run validates the request shape; it does not prove execution or upstream success. Neither check publishes a tool.
5. `publish_app_tool({toolId})` requires a fresh passing check and the same app session. Publishing a write does not execute it. `call_learned_tool({toolId,args?})` executes a published read and returns bounded, credential-scrubbed app data.
6. For a published write, call `call_learned_tool({toolId,args,requestId})` with a unique idempotency key for that exact intended action. `requestId` must contain 8–128 ASCII letters, digits, underscores or hyphens. The response has `status: "approval_required"`, an `approvalId` and a preview of the exact method, path, fixed query and newly supplied body. The approval expires within five minutes, earlier if its evidence expires. Wait for the user to approve the exact action, then use `check_approval({id: approvalId})` to obtain its execution receipt. Do not repeat `call_learned_tool` or generate a new request ID to retry. Approval, publication and dry-run validation are not execution; report success only after a successful execution receipt. A missing, failed or uncertain receipt must not trigger automatic replay.

`list_apps` includes private learned tool IDs and input schemas, so later sessions can reuse them. It also includes schemas for existing app tools. `call_app_tool({app,tool,args})` calls existing connector tools without requiring the native MCP client to refresh its initial catalog; existing writes keep their approval path. Newly learned writes use one-time exact-action approval and never inherit hour-long grants.

## Boundaries

- Reads remain limited to a conservative subset of same-origin JSON GET operations. GET alone is not treated as proof that an arbitrary endpoint is safe. Automatic write learning supports observed same-origin JSON `POST`, `PUT`, `PATCH` and `DELETE` operations accepted by the server's structural validator. Financial, payment and account-security operations are blocked until implemented as reviewed connectors. Unsupported request formats, GraphQL, login/refresh, dynamic authorities and unsupported parameters are refused; the agent must not probe a write to discover whether it works.
- Read query arguments replace values of observed keys only. Write bodies support bounded nested typed JSON, homogeneous arrays and nulls. Every observed object field is required with its captured type; extra fields are refused. Body values must come from new explicit arguments: captured body values are never copied as defaults. Writes retain their captured fixed query, which is displayed with the complete new body in the approval preview. Neither kind can change hosts, paths, methods or headers. Path-parameter templating and automatic cross-origin authentication are not supported.
- Public research has no cookies or custom authorization. Requests require HTTPS, public unicast IPs, DNS pinned to the checked address, valid TLS, exact origin, no redirects, a 10-second deadline and a 256 KiB body limit. Compressed responses are refused.
- Captured session headers are chosen server-side from observed header names. The captured connection ID, active status and session hash are checked before and after the read. Disconnect/re-login revokes old evidence, including a recreated connection with identical session JSON.
- Evidence and tools are owner scoped by the private MCP capability. There is no public verification/publish mutation. Draft specifications are immutable and never saved to the shared recipe table. Source evidence expires after one day; endpoint evidence after seven days. Publishing requires verification within ten minutes. Expired evidence/tools are pruned as new evidence/tools are created; account deletion removes evidence, tools and write intents.
- A learned write is bound to its immutable tool, full request, new arguments, connection ID and session epoch. Its complete approval preview is limited to 4 KiB; requests that cannot be shown completely are refused. Decisions require the owner's capability or verified Clerk identity, and every learned write requires one-time approval even if the profile prefers hour-long grants. A dispatch marker is committed before the single transport attempt. Stable request IDs, pending/running requests and uncertain outcomes are deduplicated; writes are never automatically retried. Watchdogs cover worker failures before and after dispatch. A timeout or lost response records an uncertain outcome rather than claiming nothing happened.
- Existing curated connectors continue to work. Previously stored legacy shared recipes are not migrated by this change. New unsupported web captures hand off privately instead of compiling globally.
- Native-only apps, absent write evidence, expired sessions, cross-origin APIs and unsupported request/response formats require user login/capture or a reviewed connector. The agent must explain this instead of inventing API behavior or success. There is no promise of autonomous payments or automatic execution of a researched endpoint.

## Account linking prerequisite

The previous `users.get` capability disclosure is removed. Google account linking now requires a verified Clerk JWT and the current device capability. Mobile uses the official Convex/Clerk bridge when Clerk is configured. Enable Clerk's Convex integration (or its `convex` JWT template with audience `convex`), and set `CLERK_JWT_ISSUER_DOMAIN` to that same Clerk instance's HTTPS Frontend API origin on each backend. Device mode remains available if verified account linking is unavailable. These checks do not constitute a migration of every legacy user-ID-only API.

## Verification

Regression coverage includes ownership, immutable revisions, fresh verification, session invalidation during reads, credential echoes (including escaped/nested JSON), endpoint constraints, query arguments, SSRF/redirect/body limits, MCP dispatch, write approval contracts, capture handoff and account-link authentication. MCP regressions distinguish structural write checks, approval-required replies and completed execution receipts, and ensure receipt checks do not resubmit a write. Real public-API and hosted-agent verification results are recorded below when run; protected consumer-app login/writes and rendered mobile interaction are separate checks.

### Real verification — November 15, 2026 Pacific

The deployed MCP workflow passed against [Open Library's public Search API documentation](https://openlibrary.org/dev/docs/api/search), without fabricated source, API responses or provider output. Real App Store search returned 17 results. Investigation extracted endpoint evidence from the documentation; the test built a draft, confirmed publication was blocked before verification, verified HTTP 200 against the real API, published privately, then changed observed query arguments and received **Pride and Prejudice** by Jane Austen. A second real device identity could neither list nor call the tool.

Both actual hosted subscription agents independently completed investigation → build → real verification → publication → parameterized call in a single turn, creating separate private tools. Claude completed in 42.8 seconds; Codex in 43.9 seconds. Durable tool events and the published private-tool records were checked, in addition to the final answer. These runs used the isolated `watchful-oyster-561` deployment and the already authorized private test identity; provider credentials and MCP capabilities are not committed.

All 142 regressions passed, along with application/Convex typechecks, full lint and diff checks. No protected consumer-app records or writes were exercised, and the rendered native capture UI has not been manually tested.

### Learned write execution — November 15, 2026 Pacific

Live verification used a temporary authenticated scratch notes API deployed alongside the isolated test backend. Its HTTP handlers persisted real note state and a mutation counter. This was a controlled test app, not Uber or another consumer account, and used no mocked transport or fabricated provider responses.

The test first performed and recorded original POST/PATCH/DELETE actions, then learned separate private write tools from those captures. Building, structural verification and publication left the mutation counter unchanged. Denial also sent no write. After authenticated exact-action approval, POST created a note, PATCH updated it and DELETE removed it. Each approval caused exactly one persisted mutation; repeated decisions, repeated request IDs and fresh IDs for the same pending request did not send another write. Foreign approval attempts and hour grants were rejected.

Both real hosted subscription agents independently inspected the capture, built a new write tool, validated it locally, published it and requested an action. Each stopped with approval pending and made no change beforehand. The test driver approved the exact scratch-note payload through the authenticated approval API. Each agent then checked the execution receipt in a follow-up turn, confirmed the persisted note and did not resubmit the write. This tested real Claude/Codex execution and the approval API; it did not test a rendered native button tap.

The scratch app, records, learned test tools and temporary HTTP handlers were removed after verification. Existing read-learning tools and subscription sessions were preserved. No real consumer-app data, ride booking or payment was modified. Financial/payment integrations still require reviewed connectors.

All 195 regressions passed, with application/Convex typechecks, full lint and diff checks. Coverage includes immutable approved payloads, owner checks, at-most-one dispatch, denial/expiry, session changes, nested JSON constraints, protected routes, complete previews, secret redaction, uncertain-outcome deduplication and watchdog recovery.
